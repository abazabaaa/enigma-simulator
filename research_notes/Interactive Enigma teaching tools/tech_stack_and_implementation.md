# Technology stack and implementation patterns for a 3D, story-driven Enigma teaching app

Research date: 2026-09-28. All npm versions/dates below were read directly from registry.npmjs.org on that date; bundle sizes from bundlephobia.com; repo metadata from the GitHub API. Where I ran experiments in the target container (Chromium at /opt/pw-browsers), they are labelled "Empirical (this container)".

## Key Question 1: Rendering framework — R3F v9 + three.js + drei vs plain three.js vs Babylon.js vs Svelte/Threlte (maintenance, size, ecosystem for glow/labels/camera/declarative animation; what explainer sites use)

### Takeaway
React Three Fiber 9.x (React 19 only) + three r186 + drei 10.x + @react-three/postprocessing 3.x is the most complete, actively maintained declarative stack for a mechanism explainer (SDF text, DOM labels, CameraControls, scroll helpers, selective bloom out of the box, Zustand bundled). Threlte 8 (Svelte 5) is a credible alternative with a smaller core; Babylon.js is far heavier unless aggressively tree-shaken; plain three.js is what the best-known hand-crafted explainers use, but costs you the component/ecosystem leverage. For declarative animation, use @react-spring/three (React 19 compatible) or GSAP (fully free since April 2025); framer-motion-3d is deprecated and theatre.js is stuck on R3F v8 peers.

**R3F v9 breaking changes (must-know for React 19)**
- v9 is "a compatibility release for React 19"; contains breaking changes under StrictMode; `Props` type renamed `CanvasProps`; hardcoded prop types like `MeshProps` removed in favour of `ThreeElements['mesh']`; JSX typing via module augmentation of `ThreeElements`; `extend` can generate components from individual classes; `gl` prop callbacks receive constructor params and may return promises (async renderers); StrictMode now inherited from parent; `act` now imported from React; automatic sRGB texture conversion removed (annotate colour textures manually); Suspense side-effect fixes — [R3F v9 migration guide](https://r3f.docs.pmnd.rs/tutorials/v9-migration-guide)
- R3F v10.0.0-alpha.1 exists: supports both WebGLRenderer and WebGPURenderer, `state.gl` becomes `state.renderer`, new scheduler, WebGPU/TSL hooks; "Consider all features experimental and may be changed, removed or expanded at any time" — [R3F discussion #3665](https://github.com/pmndrs/react-three-fiber/discussions/3665)

**Ecosystem pieces relevant to a mechanism explainer**
- Glow: `<Bloom>` is "selective by default"; make objects glow with emissive values above 1 (`emissive="red" emissiveIntensity={2}`) and `toneMapped={false}` on the material, and `luminanceThreshold={1}` so nothing else blooms; `mipmapBlur` prop recommended — [react-postprocessing docs: Bloom](https://react-postprocessing.docs.pmnd.rs/effects/bloom); a dedicated `SelectiveBloom` effect also exists — [react-postprocessing docs: SelectiveBloom](https://react-postprocessing.docs.pmnd.rs/effects/selective-bloom)
- Text in 3D: drei `<Text>` uses troika-three-text SDF rendering; suspends while loading font; pass `characters="..."` to pre-generate glyphs and avoid FOUC; `<Text3D>` for extruded text — [drei docs: Text](https://drei.docs.pmnd.rs/abstractions/text)
- DOM labels: drei `<Html>` projects DOM to object positions; `transform` (matrix3d) mode, `occlude` (incl. `"blending"` mode for real 3D occlusion), `distanceFactor`, `portal`, `zIndexRange`; caveat: in transform mode "the rendered html may appear blurry" on some devices — [drei docs: Html](https://drei.docs.pmnd.rs/misc/html)

- Declarative animation: `@react-spring/three` provides an `animated` namespace for three objects/materials; imperative `api.start()` animates "without a single react render"; `onChange` to sync external stores; known end-of-animation jank fixed by `config.precision = 0.0001` — [react-spring docs: React Three Fiber](https://www.react-spring.dev/docs/guides/react-three-fiber)
- GSAP: "Thanks to Webflow, GSAP is now 100% FREE including ALL of the bonus plugins" as of 2025-04-30; Webflow acquired GreenSock 2024-10-15 — [GSAP blog: 3.13 release](https://gsap.com/blog/3-13/); [Webflow blog](https://webflow.com/blog/gsap-becomes-free); GSAP can animate "any property of any object", not only DOM/CSS — [gsap.to() docs](https://gsap.com/docs/v3/GSAP/gsap.to()/); `useGSAP()` hook auto-reverts tweens/ScrollTriggers via `gsap.context()` on unmount (important under StrictMode), with `scope` and `contextSafe()` — [GSAP React guide](https://gsap.com/resources/React/)

### Inferences
- The stack that minimises integration risk today is React 19.3 + R3F 9.8 + drei 10.7 + @react-three/postprocessing 3.1 + three 0.186 (all released within the same week and with mutually satisfied peer ranges). Pin `three` to ≤0.186 until `postprocessing` widens its `< 0.187` peer range; this peer window historically lags each three release by days-to-weeks.
- Stay on WebGLRenderer: the glow effect depends on pmndrs `postprocessing`, which is WebGL-only, and R3F v10/WebGPU is alpha.
- Theatre.js is effectively unusable with R3F 9 (peer `^8.13.6`, no release since May 2024) and framer-motion-3d is dead; choose @react-spring/three for state-driven transitions (rotor stepping, key press) and GSAP timelines (free, `useGSAP` cleanup) for scripted multi-step "signal travels" sequences. Both tween plain three.js object properties, so they also work in `useFrame`-driven imperative code.
- Threlte 8 would be the pick if the team prefers Svelte; its core is an order of magnitude smaller than R3F's install size, but its extras ecosystem and postprocessing bindings are thinner than drei/react-postprocessing (not measured here). Babylon.js only makes sense with disciplined per-file imports; its whole-package size (1.7 MB gzip) is ~10x three.
- Ciechanowski-style hand-written WebGL is the gold standard for polish but is a multi-month artisanal effort; the two Enigma projects above show that both vanilla three.js and a component framework are viable for exactly this machine.

## Key Question 2: Procedural vs asset-based modelling of rotors, plugboard, lampboard, keyboard, reflector; animating a glowing signal path

### Takeaway
Everything in an Enigma is a solid of revolution, a box, or a cable along a curve, so procedural modelling with three.js primitives (`CylinderGeometry`, `TorusGeometry`, `Shape`+`ExtrudeGeometry` for notches/rings, `TubeGeometry` over `CatmullRomCurve3` for cables and the signal path) plus drei `<Instances>` for the 26×N contacts is feasible and keeps the site asset-free; the glowing path is a bright emissive tube (or drei `Line`/`CatmullRomLine` with `dashOffset` animation) picked up by Bloom with `luminanceThreshold=1`.

### Cited Findings
- R3F maps three.js constructors to JSX with `args` (e.g. `<sphereGeometry args={[1, 32]} />`); "if args change later on, the object must naturally get reconstructed from scratch"; geometries/materials auto-`attach`; `<primitive object={...}>` wraps pre-built objects but does not auto-dispose — [R3F docs: Objects, properties and constructor arguments](https://r3f.docs.pmnd.rs/api/objects)
- `TubeGeometry(path, tubularSegments=64, radius=1, radialSegments=8, closed=false)` extrudes a circle along any `Curve`, computing Frenet frames (`path.computeFrenetFrames()`) and per-segment UVs — [three.js source: TubeGeometry.js](https://github.com/mrdoob/three.js/blob/dev/src/geometries/TubeGeometry.js)
- `Shape` (moveTo/lineTo/bezierCurveTo/arc/holes) + `ExtrudeGeometry` (depth, bevel) is the documented way to make custom mechanical outlines such as notches, rings and plates — [three.js docs: ExtrudeGeometry](https://threejs.org/docs/pages/ExtrudeGeometry.html); [three.js docs: Shape](https://threejs.org/docs/pages/Shape.html)
- drei `<Line>` renders `THREE.Line2`/`LineSegments2` (three-stdlib) with pixel `lineWidth`, `dashed`, `vertexColors`; `<CatmullRomLine>` renders a Line2 through `CatmullRomCurve3` with `curveType` ("centripetal" default, "chordal", "catmullrom"), `tension`, `closed` — [drei docs: Line](https://drei.docs.pmnd.rs/shapes/line); [drei docs: CatmullRomLine](https://drei.docs.pmnd.rs/shapes/catmull-rom-line)
- drei bundles `meshline ^3.3.1` (meshline 3.3.1 last published 2024-06-03, MIT) as an alternative thick-line implementation — [npm registry: @react-three/drei](https://registry.npmjs.org/@react-three/drei/latest); [npm registry: meshline](https://registry.npmjs.org/meshline)
- drei `<Instances limit={n}>` wraps `InstancedMesh`, supports per-`<Instance>` `color/scale/position`, pointer events (`onClick`, `onPointerOver`), nesting, and custom attributes via `InstancedAttribute`; caveat: declarative instances "incur CPU overhead", use raw `THREE.InstancedMesh` for very high volumes — [drei docs: Instances](https://drei.docs.pmnd.rs/performances/instances)
- Selective glow recipe: `<Bloom mipmapBlur luminanceThreshold={1} />` + `meshStandardMaterial emissive="red" emissiveIntensity={2} toneMapped={false}`; non-emissive materials will not glow — [react-postprocessing docs: Bloom](https://react-postprocessing.docs.pmnd.rs/effects/bloom)
- Existence proofs: owenautosport/enigma-bombe builds the Enigma and a 36-drum Bombe in three.js r128 with "signal tracing visualization", models "built to published dimensions (1 unit = 1 cm)" from photographs — [owenautosport/enigma-bombe](https://github.com/owenautosport/enigma-bombe); reimunyancat/enigma has an "X-ray mode exposing internal wiring", "the last keypress traces its exact current path", drag-and-drop plugboard cables, key depression animation, "on-demand rendering and automatic quality scaling" — [reimunyancat/enigma](https://github.com/reimunyancat/enigma)
- R3F discussion on moving objects along a path uses `Curve.getPointAt(t)` in `useFrame` — [R3F discussion #713: Animation along a path](https://github.com/pmndrs/react-three-fiber/discussions/713)
- Selective bloom confusion is common; three.js forum threads document layer-mask vs emissive-threshold approaches — [three.js forum: selective bloom on parts of a glTF in R3F](https://discourse.threejs.org/t/react-3-fiber-adding-selective-bloom-effect-to-parts-of-imported-gltf-model/43726)

### Inferences
- Model plan (all procedural, one shared material set): rotor body = `cylinderGeometry`; alphabet ring = 26 `<Text>` glyphs (troika SDF) parented to the rotor so they rotate with it, or one baked ring texture; contacts = one `<Instances>` of 26 pins per rotor face (26×(3 rotors×2 faces + reflector + ETW) ≈ 200 instances, one draw call); notch = `Shape` with a cut-out extruded as a ring; plugboard = 26 sockets as `<Instances>` and cables as `tubeGeometry` over a `CatmullRomCurve3` between two socket positions with a sag control point; lampboard = 26 `<Instances>` with per-instance `color`, lit lamp gets emissive > 1; keyboard = 26 instanced key caps with a spring-driven `position.y`.
- Signal path: build one `CatmullRomCurve3` through the actual wiring hops (key → plugboard → ETW → rotor contact in/out per rotor → reflector → back), render a `tubeGeometry` with emissive material (glows under Bloom threshold 1), and animate a "head" by scrubbing a `drawRange`/`dashOffset` (drei `Line` supports `dashed`) or by moving a small emissive sphere with `curve.getPointAt(t)`; because `args` changes rebuild the geometry, memoise the curve per (settings, key) and only mutate uniforms/dash offsets per frame.
- Geometry rebuilds are cheap at this scale (a few thousand vertices); an asset pipeline (Blender/glTF) adds bytes and toolchain but is unnecessary for a schematic-realistic machine.

### Gaps
- I found no published R3F tutorial of a procedurally modelled mechanical device (gears/rotors); search returned generic geometry guides only. Feasibility is inferred from the geometry APIs and the two Enigma repos rather than a worked example.
- The drei Line docs did not surface a `dashOffset` animation example; the prop exists on `LineMaterial` (three-stdlib) but I did not verify the exact animation idiom.

## Key Question 3: Story/lesson architecture — chapter/scene state machines, scroll vs click, progress persistence, gating, interactive-textbook frameworks

### Takeaway
Model the lesson as an XState v5 machine (chapters as states, "check passed" as guarded transitions) persisted with `getPersistedSnapshot()` to localStorage, and keep transient 3D/UI state in Zustand (already a drei dependency). Prefer click/step-gated scenes with optional scroll-driven camera moves via drei `ScrollControls`; Idyll is dormant (last push 2023), Observable Framework is a data-app SSG rather than a lesson engine, so MDX + custom components is the practical "interactive textbook" layer.

### Cited Findings
- XState v5: `actor.getPersistedSnapshot()` returns a JSON-serialisable snapshot; restore with `createActor(machine, { snapshot })`; snapshot "includes child state, so a restored actor restores its children too" — [Stately docs: Persist and restore actors](https://stately.ai/docs/xstate/v6/persist-and-restore-actors); [Stately blog: Persisting and restoring state](https://stately.ai/blog/2023-10-02-persisting-state); a known bug: restoring from a serialised snapshot breaks history-state behaviour — [xstate issue #5178](https://github.com/statelyai/xstate/issues/5178)
- Versions: `xstate` 5.33.2 (2026-09-15, MIT), `@xstate/react` 6.1.0 (2026-02-26; peers `xstate ^5.28`, react 16.8–19), `@xstate/store` 4.2.3 (2026-08-10); `zustand` 5.0.15 (2026-08-13, MIT; peers react >=18) — [npm registry: xstate](https://registry.npmjs.org/xstate); [npm registry: zustand](https://registry.npmjs.org/zustand)
- drei `<ScrollControls pages damping distance horizontal infinite>` + `useScroll()` giving `offset`, `delta`, `range(start,len)`, `curve(start,len)`, `visible(start,len)`; `<Scroll html>` scrolls DOM alongside the canvas; canvas content outside `<Scroll>` does not scroll — [drei docs: ScrollControls](https://drei.docs.pmnd.rs/controls/scroll-controls)
- GSAP ScrollTrigger is included in the free GSAP and is auto-cleaned by `useGSAP()` — [GSAP React guide](https://gsap.com/resources/React/); [GSAP 3.13 blog](https://gsap.com/blog/3-13/)
- Scrollama 3.2.0 (npm 2022-06-17, MIT) is IntersectionObserver-based scrollytelling with step enter/exit/progress callbacks and a built-in resize observer; repo pushed 2025-11-13, 6,003 stars — [russellsamora/scrollama](https://github.com/russellsamora/scrollama); [npm registry: scrollama](https://registry.npmjs.org/scrollama)
- Idyll: npm latest 6.0.0-alpha.6 published 2022-04-22 (MIT); repo last pushed 2023-02-04, 2,041 stars, 60 open issues, not archived — [npm registry: idyll](https://registry.npmjs.org/idyll); [idyll-lang/idyll](https://github.com/idyll-lang/idyll)
- Observable Framework 1.13.4 (2026-03-02, ISC): "free, open-source static site generator for data apps, dashboards, and reports"; Markdown + reactive JavaScript; data loaders precompute snapshots at build; deploys as static HTML — [observablehq/framework](https://github.com/observablehq/framework); [npm registry](https://registry.npmjs.org/@observablehq/framework)
- `@mdx-js/react` 3.1.1 (2025-08-29, MIT) — [npm registry: @mdx-js/react](https://registry.npmjs.org/@mdx-js/react)
- Guided-tour pattern in the wild: enigma-bombe's tour "dims the page, lights up the control you need to press next" with an optional "Do it for me" auto-execute — [owenautosport/enigma-bombe](https://github.com/owenautosport/enigma-bombe); JashanMaan28/enigma-simulator persists settings locally and uses a reducer for state — [JashanMaan28/enigma-simulator](https://github.com/JashanMaan28/enigma-simulator)
- R3F performance docs recommend React `startTransition` for expensive state changes and show React scheduling holding ~60 fps vs 5–20 fps for naive approaches — [R3F docs: Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)

### Inferences
- Architecture: one `lessonMachine` (XState) with a state per chapter and nested states per step; `CHECK` events carry the learner's answer, guards evaluate it against the engine, and `NEXT` is only enabled from a `passed` sub-state — this makes "next chapter unlocks only after the check passes" a property of the machine rather than scattered UI conditions, and it is unit-testable in Vitest without rendering. Persist the actor snapshot to localStorage on every transition; version the snapshot key so a machine refactor cannot rehydrate a stale shape (and avoid XState history states given issue #5178).
- Keep machine-state for the Enigma itself (rotor positions, plugboard) in a plain TypeScript engine + a Zustand store subscribed by R3F components; drive animations from store changes with react-spring so the lesson machine never needs to know about three.js.
- Click/step gating fits better than scroll-driven for a mechanism whose steps must be completed; use scroll only for cinematic camera moves between chapters (drei ScrollControls or GSAP ScrollTrigger on a sticky canvas), and provide equivalent "Next" buttons for keyboard/reduced-motion users.
- Content layer: MDX chapters compiled at build time by Vite with custom components (`<Machine step=...>`, `<Check id=...>`); this keeps prose in Markdown while chapters remain lazily-loadable React modules. Idyll and Observable Framework do not add enough over MDX for a single-app lesson and would fight the React/R3F component model.

## Key Question 4: In-browser code exercises (Monaco/CodeMirror 6 + sandboxed runner; Pyodide; Sandpack) — cost/complexity

### Takeaway

### Inferences
- Recommended: CodeMirror 6 (`@codemirror/lang-javascript`, one-dark theme) + a dedicated Web Worker that receives the learner's source, wraps it as a function with a fixed signature (e.g. `step(rotorPositions)`), runs it with a timeout (terminate the worker on overrun), and compares results against the reference engine's outputs for fixed test vectors. Because this is a same-origin static site with no secrets, a Worker is an adequate sandbox; QuickJS-WASM is the upgrade if you want deterministic time limits and no access to DOM/network at all.
- TypeScript exercises need an in-browser transpile step (esbuild-wasm or `typescript`'s `transpileModule`); both are multi-hundred-kB additions — start with JavaScript.
- Pyodide only if lessons must be in Python: budget ~6–15 MB first load, lazy-load it in the exercise chapter only, and self-host under `public/pyodide/` (Pages serves `.wasm` with the correct MIME; verify) or use the jsDelivr CDN.
- Sandpack is designed for full React/Node-style projects and its separate-origin bundler requirement means a second Pages site or CodeSandbox's hosted bundler; overkill for 10-line cipher exercises.

### Gaps
- I did not find a primary Monaco bundle-size figure; the "2–5 MB" numbers come from secondary comparison articles.
- Whether GitHub Pages serves `.wasm` with `application/wasm` was not verified in this research.

## Key Question 5: Testing — WebGL in headless Chromium under Playwright, visual regression, testing via exposed app state, unit-testing the engine with published vectors

### Takeaway
In this container (Playwright browsers rev 1194 = Chromium 141.0.7390.37), WebGL 1 and 2 both work in headless Chromium **with no extra flags**, rendering through SwiftShader; adding `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader` is harmless and future-proofs against Chrome's SwiftShader-fallback removal, while `--use-angle=gl` (a common blog recommendation) breaks context creation when the raw binary is launched without a GPU. Test the machine through an exposed state API (`window.__enigma`) and reserve pixel snapshots for a few masked, same-environment baselines; unit-test the engine in Vitest with the AAAAA→BDZGO, ADU double-step and Barbarossa vectors.

### Cited Findings
**Empirical (this container, 2026-09-28)**
- `/opt/pw-browsers` contains `chromium-1194` and `chromium_headless_shell-1194`; both report `Chromium 141.0.7390.37`; `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`; Node v22.22.2 (Bash session in this container).
- Raw binary probe (`--headless=new --no-sandbox --dump-dom` on a page that creates `webgl2` and `webgl` contexts, clears to red and `readPixels`): headless_shell and full chrome both returned `webgl2: OK` and `webgl: OK`, renderer `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`, `readPixels=255,0,0,255` with **no flags**, and identically with `--enable-unsafe-swiftshader`, `--use-gl=angle --use-angle=swiftshader`, `--use-angle=swiftshader-webgl --enable-unsafe-swiftshader`, `--ignore-gpu-blocklist`. **Chromium/Playwright documentation**
- Chromium: automatic WebGL fallback to SwiftShader is deprecated because it is "a high security risk due to JIT-ed code running in Chromium's GPU process"; opt in with `--enable-unsafe-swiftshader`; flag combos `--use-gl=angle --use-angle=swiftshader-webgl --enable-unsafe-swiftshader` or `--use-gl=angle --use-angle=swiftshader`; SwiftShader is "a useful tool for web developers to test their sites on systems that are headless or do not have a supported GPU" but only by opt-in — [Chromium docs: Using Chromium with SwiftShader](https://github.com/chromium/chromium/blob/main/docs/gpu/swiftshader.md)
- The removal "ships on Desktop 137"; affects ~2.7% of WebGL contexts (~0.5% of page loads); CI without GPU should use `--enable-unsafe-swiftshader`; sites should "handle WebGL context creation failure and fall back to other web APIs such as Canvas2D or an appropriate message" — [blink-dev: Intent to Remove: SwiftShader Fallback](https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM); Edge 144 likewise fails context creation where SwiftShader would be used — [Microsoft Learn: EnableUnsafeSwiftShader policy](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/enableunsafeswiftshader)

- With a real GPU present, `--use-angle=gl` raised a WebGL aquarium from 8 fps to 60 fps in headless Playwright (Docker needs NVIDIA Container Toolkit) — [createIT: Headless chrome – testing WebGL using Playwright](https://www.createit.com/blog/headless-chrome-testing-webgl-using-playwright/); `--use-gl=egl` / `--use-gl=desktop` cut per-test time 1.9 s→1.3 s on macOS with `channel: "chrome"` — [Michel Krämer: Enable GPU for slow Playwright tests](https://michelkraemer.com/enable-gpu-for-slow-playwright-tests-in-headless-mode/); Linux hardware path: `--use-angle=vulkan --enable-features=Vulkan --disable-vulkan-surface --enable-unsafe-webgpu` — [Dave Snider: Running Playwright with GPU powered Actions](https://davesnider.com/gputests)
- Known failure signature on macOS GitHub Actions: "Could not create a WebGL context... BindToCurrentSequence failed" with ANGLE/Vulkan/SwiftShader; closed referencing PR #30937, no workaround given — [microsoft/playwright issue #30585](https://github.com/microsoft/playwright/issues/30585)
- Visual comparisons: `toHaveScreenshot` with `maxDiffPixels`/`maxDiffPixelRatio`, `stylePath` to hide dynamic elements; snapshot names include browser and platform; "For consistent screenshots, run tests in the same environment where the baseline screenshots were generated" — [Playwright docs: Visual comparisons](https://playwright.dev/docs/test-snapshots)

- Published vectors used by these suites: default key (UKW-B, rotors I II III, rings 01 01 01, start AAA, no plugs) `AAAAA → BDZGO`; double-step sequence `ADU → ADV → AEW → BFX → BFY` ("removing the double step makes 10 tests fail"); Operation Barbarossa message of 7 July 1941 (Sullivan & Weierud, Cryptologia); cross-check vectors generated with py-enigma — [JashanMaan28/enigma-simulator](https://github.com/JashanMaan28/enigma-simulator); nine historical messages incl. 1930 manual example, both Barbarossa parts, Scharnhorst, U-264/U-623/U-534, Dönitz, verified against two independent simulators — [lucasrada/enigma](https://github.com/lucasrada/enigma)

### Inferences
- Playwright config for this container: `use: { launchOptions: { args: ['--use-gl=angle','--use-angle=swiftshader','--enable-unsafe-swiftshader','--ignore-gpu-blocklist'] } }` with the default headless shell; do **not** add `--use-angle=gl`/`--use-gl=egl` unless a GPU is present. ## Key Question 7: Accessibility and performance — reduced motion, keyboard operation, mobile viewport, draw-call budgets, instancing

### Takeaway
Treat the 3D canvas as a visualisation of a fully keyboard-operable DOM machine: real `<button>` keys, a live region announcing lamps, and reduced-motion detection that swaps animated signal paths for instant state changes; performance-wise, R3F's guidance is a few hundred draw calls, on-demand rendering, instancing for the ~200 contacts/26 lamps/26 keys, and DPR/effect degradation via `PerformanceMonitor`.

### Cited Findings
- WCAG 2.2 SC 2.1.1 Keyboard (Level A): "All functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes", except path-dependent input such as freehand drawing; dragging to a location is not exempt — [W3C Understanding SC 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)
- `prefers-reduced-motion: reduce` detectable with `window.matchMedia("(prefers-reduced-motion: reduce)").matches` and a `change` listener; guidance is to remove, reduce or replace vestibular triggers (scaling, panning large objects) e.g. swap a scale pulse for an opacity change, rather than removing all motion — [MDN: prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)
- `@react-three/a11y`: `<A11y role="button|togglebutton|link|content">` wrappers give focus indication, tab index, keyboard activation (Enter etc.), `description`/`showAltText`, an `<A11yAnnouncer>` next to the Canvas for screen readers, and user-preference detection (motion/colour scheme) — [react-three-a11y README](https://github.com/pmndrs/react-three-a11y); npm latest 3.0.0 published 2022-05-15 (peers `@react-three/fiber >=8.0`, react >=18) — [npm registry](https://registry.npmjs.org/@react-three/a11y); repo pushed 2026-08-20, 626 stars, GitHub license field "Other/NOASSERTION" while npm says MIT — [GitHub API: pmndrs/react-three-a11y](https://github.com/pmndrs/react-three-a11y)
- Alternative pattern: drei `<Html>` with `opacity: 0` so 3D hotspots get real focusable DOM elements and labels — [react-three-a11y search summary / PR example](https://github.com/NIRANKEN/threejs-profile-test/pull/47)
- Chris Coyier's critique of Ciechanowski's posts: "the sliders are largely unfocusable `<div>` situations" — [CSS-Tricks](https://css-tricks.com/bartosz-ciechanowskis-interactive-blog-posts/)
- R3F performance guidance: `frameloop="demand"` + `invalidate()` ("merely requests a new frame"); share geometries/materials; draw-call budget "optimal maximum: ~1000, ideally a few hundred"; `InstancedMesh` for hundreds of thousands of objects in one call; drei `<Detailed>` LOD; `PerformanceMonitor` `onIncline/onDecline` to adjust `dpr` or toggle effects; `regress()` during interaction; `startTransition` for expensive updates — [R3F docs: Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)

- JashanMaan28/enigma-simulator's Playwright suite runs desktop and mobile projects with accessibility scanning — [JashanMaan28/enigma-simulator](https://github.com/JashanMaan28/enigma-simulator); reimunyancat/enigma implements "on-demand rendering and automatic quality scaling" — [reimunyancat/enigma](https://github.com/reimunyancat/enigma)
- JashanMaan28's simulator states all data persists locally in browser storage with no external transmission — [JashanMaan28/enigma-simulator](https://github.com/JashanMaan28/enigma-simulator)

### Inferences
- Make the DOM the source of truth for operation: a visually-hidden (or visible on mobile) `<div role="group" aria-label="Keyboard">` of 26 `<button>`s, rotor `<input type=number>`/spinbuttons, plugboard as a `<select>` pair list; the 3D scene mirrors the store. This satisfies 2.1.1 without relying on the 2022-era @react-three/a11y package (still usable: its peer range `>=8` admits fiber 9, and the repo saw pushes in Aug 2026).
- Announce each keypress result in an `aria-live="polite"` region ("Q lights up as E; rotors now A E W") — cheap and testable in Playwright.
- Reduced motion: read `matchMedia` once into the store; when true, set react-spring `immediate`, GSAP `duration: 0`/`gsap.matchMedia`, disable Bloom flicker and camera fly-throughs, and render the signal path fully drawn instead of animated.
- Mobile: cap `dpr={[1, 1.5]}`, use `PerformanceMonitor` to drop Bloom on decline, `frameloop="demand"` when idle, and give the canvas a fixed aspect box above the lesson text rather than a full-bleed hero on phones.
- Draw calls: instanced contacts (~200), lamps (26), keys (26), sockets (26) plus a dozen unique meshes yields <100 draw calls; Bloom adds a few full-screen passes — within budget even on SwiftShader for tests.

### Gaps
- No source measured actual frame rates of an R3F Enigma-sized scene on mobile or under SwiftShader; the budget numbers are R3F's general guidance.
- @react-three/a11y's compatibility with React 19/R3F 9 is inferred from peer ranges only; I found no changelog confirming it.

### Inferences
- Write your own small TypeScript engine (it is ~150 lines) and use three *independent* oracles in CI: (1) `@ondoher/enigma` (MIT, npm, hooks into each stage — useful for asserting intermediate contacts shown in the 3D signal path), (2) cryptii's Enigma brick (MIT; import from the repo or vendor the wiring tables) and (3) py-enigma via a one-off script that generates a JSON vector file committed to the repo (covers rotors IV/V, ring settings, long texts). Hard-code the published vectors (AAAAA→BDZGO; ADU→ADV→AEW→BFX→BFY; Barbarossa) as regression tests.
- Do not reuse lucasrada/enigma or JashanMaan28/enigma-simulator code: both are days old and carry no licence, so they are all-rights-reserved by default; they are, however, excellent *test-design* references (property tests, mutation list, Playwright e2e).
- For the Bombe chapter, enigma-bombe (MIT) is the only permissively licensed JS reference with a diagonal board; its architecture (menu→drum stacks→test register, 60 wheel orders) can be reused or re-implemented against its test vectors, but it is one day old with one star, so verify its Bombe results against the historical wheel orders it claims before trusting it as an oracle.
- Palloks' simulator remains the best manual cross-check for exotic models but its bespoke licence (attribution + mark modifications) and 2019 date make it a reference, not a dependency.

### Gaps
- I did not execute any of these libraries to confirm the BDZGO/ADU vectors myself; accuracy claims are as stated in their READMEs.
- Licence status of lucasrada/enigma, JashanMaan28/enigma-simulator and reimunyancat/enigma is "none detected" by GitHub's API; a LICENSE file may exist under a non-standard name.
- Weekly download counts and CI status for the npm packages were not retrievable (npmjs.com pages returned 403).

## Overall recommendation: concrete stack and versions (synthesis)

### Takeaway
React 19.3 + Vite 8.3 + TypeScript; three 0.186 + R3F 9.8 + drei 10.7 + @react-three/postprocessing 3.1 (WebGL, Bloom threshold-1 glow); @react-spring/three 10.1 for state transitions and GSAP 3.15 (`@gsap/react`) for scripted sequences; XState 5.33 for the lesson machine persisted to localStorage, Zustand 5 for machine/UI state; MDX 3 chapters lazy-loaded; CodeMirror 6 + Web Worker/QuickJS-WASM for exercises; Vitest 5 + @react-three/test-renderer 9 + Playwright 1.63 (SwiftShader flags) for tests; GitHub Actions → Pages with `base: '/<REPO>/'`.

### Cited Findings
- All version/date/licence facts are cited in Key Questions 1–8 above (npm registry reads on 2026-09-28) — [npm registry](https://registry.npmjs.org/)
- Peer-range compatibility chain: fiber 9.8.1 requires react ≥19 <19.4 and three ≥0.156; drei 10.7.9 requires fiber ^9, three ≥0.159; react-postprocessing 3.1.3 requires fiber ≥9.7.0 and postprocessing ^6.36; postprocessing 6.39.5 requires three ≥0.168 <0.187 — [npm registry entries cited in KQ1](https://registry.npmjs.org/@react-three/postprocessing/latest)
- Vitest 5 requires Node ≥22.12 and Vite ≥6.4 — [Vitest 5 blog](https://vitest.dev/blog/vitest-5.html)

### Inferences
- Lock file discipline: pin `three` and `postprocessing` exactly and bump them together; run the WebGL smoke test and the engine vectors on every dependency bump.
- Avoid: framer-motion-3d (deprecated), theatre.js (R3F 8 only, dormant since 2024), Idyll (dormant since 2023), Babylon whole-package imports (1.7 MB gz), WebGPU/R3F v10 (alpha, no pmndrs postprocessing), Sandpack (separate-origin bundler).
- Optional later additions: @react-three/a11y (if the DOM-mirror approach proves insufficient), Pyodide (only for Python lessons, lazy-loaded), Threlte (if the team switches to Svelte).

### Gaps
- No single published case study covers a mechanism explainer built on exactly this stack; the recommendation composes documented capabilities rather than following a proven template.
